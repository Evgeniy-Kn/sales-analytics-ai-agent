# Анализ работы отдела продаж: amoCRM + телефония + AI-агенты

## 1. Архитектура решения

**Принцип:** агент там, где нужны решения, детерминированный workflow там, где нужна надёжность. Все цифры считаются детерминированно, кодом (SQL-запросами к БД), а не LLM; LLM работает с неструктурированными данными (разговоры, запрос руководителя, выводы). Звонки обрабатываются фоном по мере поступления, поэтому запрос «за 30 дней» — это анализ уже готовых данных за минуты, а не часы.

**Платформа:** сама архитектура от платформы не зависит; в этом решении она реализуется в n8n, включая AI-агентов. Это даёт быстрый запуск и наглядность: каждый шаг виден и отлаживается в интерфейсе. Если при разработке n8n упрётся в ограничения (сложная логика агента, нагрузка, тестирование), отдельные компоненты можно вынести в код, например переписать агента-аналитика на Python с агентным фреймворком. Компоненты связаны только через БД и инструменты, поэтому перенос можно делать по частям, не переделывая всю систему.

**Интерфейс:** для примера взят Telegram-бот, через который руководитель общается с агентом.

### Фоновый контур

- **CRM-сборщик** синхронизирует данные amoCRM в PostgreSQL: сделки (`/api/v4/leads`), задачи (`/api/v4/tasks`), историю смены этапов (`/api/v4/events`), звонки — примечания `call_in`/`call_out` у сделок и контактов (`/api/v4/leads/notes`, `/api/v4/contacts/notes`). У API лимит ~7 запросов/сек и страницы по 250 записей, поэтому данные забираются фоном, а не в момент запроса.
- **Обработчик звонков** получает запись через API телефонии, отсеивает короткие и пропущенные звонки и отправляет запись в STT.
- **Агент-аналитик звонков** оценивает каждый звонок по чек-листу: выявление потребности, работа с возражениями, договорённость о следующем шаге. Также он определяет причину отказа из фиксированного списка, ставит флаг конфликта и сохраняет ключевую цитату. Если в разговоре договорились о следующем шаге, а задачи в amoCRM нет, звонок помечается как «обещание без задачи». Краткая оценка пишется примечанием в карточку сделки, аудио удаляется.

### Контур запроса

Руководитель пишет в Telegram-бот. **AI-агент-аналитик** (узел AI Agent в n8n) сам решает, какие данные ему нужны, и вызывает инструменты — sub-workflow с готовыми SQL-запросами к PostgreSQL: воронка и конверсия, сделки без задач и с просрочками, статистика звонков, оценки звонков, поиск звонков с цитатами.
Если агент замечает аномалию, например у одного менеджера конверсия вдвое ниже, он сам углубляется в неё и подкрепляет вывод цифрами и цитатами.

Ограничения агента: цифры в отчёте берутся только из результатов инструментов (LLM ничего не считает сама), доступ к БД только на чтение, лимит числа вызовов инструментов, бот отвечает только руководителям из белого списка.

Результат: краткая сводка в Telegram и полный отчёт файлом.

### Хранение

- **amoCRM** — источник истины по сделкам и задачам и витрина для менеджеров (оценки звонков в карточке).
- **PostgreSQL** — собственная БД системы.

Своя БД нужна, потому что в amoCRM негде хранить транскрипты и оценки звонков, а API не умеет связывать и агрегировать данные: сделки, задачи и звонки приходят отдельными запросами по 250 записей.

Для небольшого отдела на этапе MVP данные сделок и задач можно брать из API amoCRM напрямую, храня в БД только результаты обработки звонков; полная синхронизация нужна по мере роста объёма.

Также в БД хранятся история отчётов и память диалогов с руководителем.

### Распознавание и 152-ФЗ

Записи и транскрипты — персональные данные, поэтому зарубежные сервисы не используются.

- **Основной вариант:** российский облачный STT (Yandex SpeechKit или SaluteSpeech) и LLM российского провайдера по договору поручения обработки.
- **Альтернатива:** self-hosted (faster-whisper + открытая LLM на сервере компании), если ИБ не разрешает передавать записи внешним провайдерам. Архитектура при этом не меняется.
- В первую очередь стоит проверить, нет ли распознавания у текущего провайдера телефонии.

Окончательный выбор согласуется с юристом и ИБ компании.

## 2. Что система делает сама, а что передаёт человеку

**Сама:** собирает данные, транскрибирует и оценивает звонки, считает метрики, находит проблемные места (сделки без задач и с просрочками, «обещания без задачи», пропущенные без перезвона), готовит отчёт и отвечает на уточняющие вопросы.

**Человеку** остаётся всё, где нужно решение, а не расчёт, или где ошибка дорого стоит. Прежде всего это решения по сотрудникам: система покажет цифры и примеры из звонков, но хорошо или плохо работает менеджер, решает руководитель. Если по какому-то звонку нужно что-то предпринять, руководитель сначала сам его слушает. Чек-лист и список причин отказа утверждает руководитель отдела, он же разбирает случаи, когда менеджер не согласен с оценкой. Этапы и задачи в amoCRM система не меняет: она только добавляет в карточку сделки примечание с оценкой звонка и подсвечивает, на что обратить внимание.

**Главные риски**, как я их вижу:

1. Ошибки распознавания и оценки. Шум на линии, названия, жаргон, да и оценка по чек-листу отчасти субъективна. Поэтому все цифры считаются SQL-запросами, а не моделью, к выводам в отчёте прикладываются цитаты и ссылки на сделки, а перед запуском оценки системы сверяются с тем, как те же звонки оценил руководитель. Дальше часть звонков периодически проверяется вручную.
2. Персональные данные. Записи звонков подпадают под 152-ФЗ, поэтому обработка идёт только на российских сервисах или своих серверах, аудио после распознавания удаляется, в LLM уходит минимум данных. Клиенты должны знать, что разговор записывается, а сотрудники должны знать, что их звонки анализируются.
3. Качество данных в amoCRM. Если менеджеры не ставят задачи или звонки не привязаны к сделкам, отчёт получится аккуратным, но неправильным. Поэтому система считает, насколько полные данные, и прямо пишет в отчёте, если выводам нельзя доверять.

## 3. Код: сделки без задач или с просроченными задачами

Скрипт [`amocrm_problem_deals.py`]([amocrm_problem_deals.py](https://github.com/Evgeniy-Kn/sales-analytics-ai-agent/blob/main/amocrm_problem_deals.py)) (Python, `requests`) берёт данные напрямую из API amoCRM. Он забирает все сделки и все незавершённые задачи по сделкам, отбрасывает закрытые сделки (системные статусы 142 и 143) и для каждой открытой сделки находит срок ближайшей задачи. Если задач нет или ближайшая уже просрочена, сделка попадает в результат.

Что учтено: пагинация по 250 записей, пауза между запросами под лимит API (около 7 запросов в секунду), ответ 204 без тела, который amoCRM на практике отдаёт, когда записей нет. Авторизация через долгосрочный токен приватной интеграции, чтобы не раздувать пример OAuth-логикой.

В рабочей системе этот же запрос живёт в CRM-сборщике: данные забираются инкрементально по `updated_at`, а не целиком, и проверка делается SQL-запросом к своей БД.

## 4. Реальный AI-проект: автоподбор тематик страниц для сайтов

**Задача.** Понять, какие страницы стоит добавить на сайт, опираясь на реальные поисковые запросы, а не на догадки. На вход подаётся домен, на выходе получается список новых тем с предложенными URL, которые сразу уходят на генерацию страниц.

**Как устроено.** Система собрана в n8n из четырёх процессов. Сначала забираются реальные запросы пользователей из Google Search Console через API. Если их мало, похожие запросы добираются через SerpAPI, а если пусто и там, используется заготовленный список типовых страниц для тематики. Запросы группируются в кластеры через API сервиса Арсенкин. Дальше работает цепочка AI-агентов: первый определяет тематику сайта и вычищает мусор, бренды конкурентов и запросы не на том языке; второй сравнивает кластеры с существующими страницами из sitemap.xml и решает, закрыта ли тема или нужна новая страница, сразу предлагая её адрес. Последний шаг отбирает пять самых перспективных новых тем. Ответы моделей приходят в фиксированном JSON, а каждая ошибка (нет доступа к Search Console, сайт отдаёт 403, нет sitemap, модель вернула невалидный ответ) получает понятный статус в Google Таблице и не останавливает обработку остальных сайтов.

**Стек:** n8n, Google Search Console API, SerpAPI, API Арсенкина, LLM через AI Agent в n8n со structured output, Google Sheets.

**Результат.** Система работала на реальных сайтах компании: вместо ручного анализа запросов и сверки со структурой сайта план новых страниц собирается автоматически и передаётся дальше на генерацию.

Принцип тот же, что в архитектуре выше: данные собираются и обрабатываются обычными интеграциями, а модель подключается только там, где нужно содержательное решение.

Сам проект собран в n8n, поэтому кода в репозитории нет. Как пример моего кода на Python можно посмотреть [Telegram-бот для учёта тренировок](https://github.com/Evgeniy-Kn/my_gym_tracker_bot_pub): aiogram 3, асинхронный SQLAlchemy, графики прогресса по упражнениям на matplotlib.

## 5. Чему научился самостоятельно за последние полгода

**Работе с Claude Code в связке с n8n.** Подключил Claude Code к n8n через официальный MCP-сервер и стал отдавать ему сборку воркфлоу: ставлю конкретную задачу, агент сам собирает процесс в n8n, а я проверяю результат и правлю то, что не устраивает. Сборка рабочих процессов заметно ускорилась, а моя роль сместилась от ручной расстановки узлов к постановке задачи и проверке. Использую этот подход в текущих проектах на n8n.

**Cloudflare и его API.** До этого с Cloudflare не работал вообще, разобрался с нуля под задачу в пайплайне генерации сайтов. Через API автоматизировал всю публикацию: создание зоны для домена, настройку DNS, подключение домена к Cloudflare Pages и запуск деплоя. В итоге сайт от готовых файлов до работы на своём домене публикуется без ручных действий в панели.

## 6. Улучшение, которое я предложил и довёл до результата

Мы генерировали однотипные сайты на WordPress, и после генерации страниц сотрудники вручную собирали на каждом сайте меню в шапке: добавляли базовые страницы, выстраивали порядок и вложенность. Работа рутинная, занимала время на каждом сайте, и в ней легко было ошибиться.

Я предложил встроить сборку меню в сам процесс генерации и сделал это в n8n. После того как страницы созданы, отдельный шаг собирает меню из базовых страниц через REST API WordPress и назначает его в шапку сайта. Сайты обрабатывались параллельно, поэтому процесс пришлось строить так, чтобы данные одного сайта не смешивались с данными другого: всё нужное передаётся вместе с самим элементом, а не через общие переменные.

В результате меню появлялось на сайте сразу после генерации страниц, а ручной шаг из процесса ушёл совсем.
